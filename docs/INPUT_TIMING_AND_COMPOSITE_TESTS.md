# 输入时机与复合测试

TestConductor 不把所有输入混成一个“大 JSON”。输入在三个时间点进入系统。

## 1. 输入测试意图：生成测试计划

来源是需求文本或需求文件，允许自然语言、Markdown、表格、JSON/YAML、DOCX/PDF 等格式。
前端选择测试资源配置和测试渠道；系统从资源配置取得内部目标标识与环境值，用户不单独填写
“测试环境”。测试类型与具体要求写在需求正文中。

```yaml
requirements:
  - requirement_id: REQ-LOGIN-LOCK
    content: 对登录锁定执行边界和异常测试；连续错误密码达到阈值后锁定账号
target:
  system_id: account-web
  environment: staging
selections:
  techniques: []
  allowed_channels: [api, ui, database]
```

第一层模型把测试意图转换为审核用的详细测试计划：场景、业务操作、预期结果、数据需求和清理目标。
此时不读取 OpenAPI、SQL 或真实密码。
这里的测试计划不是分类提纲：操作必须说明对哪个业务对象做什么，预期必须说明在对应操作后检查什么，
并列出所需测试数据及约束；但不提前写 locator、HTTP 请求、SQL 或压测脚本。

## 2. 资源输入：生成执行计划

资源是“怎样执行”的可信来源，在第二层开始前解析：

| 渠道 | 输入 | 作用 |
| --- | --- | --- |
| UI | URL/功能/最大步数资料 | 限定网页 Agent 的目标与步数 |
| API | OpenAPI 或接口说明/文档、基础地址 | 整理 method、path、参数和响应观察项 |
| 数据库 | DDL、数据字典、表结构说明或规范策略、连接引用 | 整理允许访问的方言、表、字段和运行参数 |
| 性能 | 性能要求、历史方案、现有配置或规范 Profile | 整理目标、负载安全上限、driver 和指标 |
| 端口 | 主机和端口 | 登记单个 TCP 探测目标 |

这些资料不要求用户手写内部 schema：标准格式确定性解析，其他常见文档和文字由模型规范化。
资源输入不放密码、连接串、SQL 运行结果或本机绝对路径。审批测试计划并生成执行计划时，
页面同时接收可选的本次变量（每行 `名称=值`），并把它们冻结到执行计划中。UI 可能事先不知道全部输入，页面会提醒未注明输入可能被模型编造。测试网站账号密码也在此填写。
执行计划页面会展示这些输入以及 UI Agent Action/Check、SQL、接口调用或压测参数；若包含
数据库写 SQL，会额外展示高风险提示。审批通过后立即执行，写操作会修改测试环境数据。
第二层 AI 对所有渠道采用同一原则：测试计划决定测什么，测试资产限制怎样测，冻结输入提供本次数据；
最终生成可执行实现和断言，输入值只通过变量绑定使用，不硬编码到 SQL、URL 或脚本。
网页 Agent 资产不声明业务状态影响，因此相关能力在 Catalog 中明确标为
`unknown`，由计划审核人结合第一层 `state_impact` 和 cleanup 目标核对；系统不会根据资产
名称猜测。API、数据库、性能和端口资源仍执行确定性状态影响校验。

## 3. 执行时注入

执行时不再要求人工填写变量或 JSON。普通变量和测试网站账号来自已审批执行计划中的冻结输入；
数据库连接、平台密钥、性能 driver、性能运行模式和 cleanup hook 使用
`TEST_PLATFORM_RUNTIME_CONTEXT_FACTORY` 或部署环境注入。
失败后原样重试会复用同一份冻结输入；需要改变输入或执行内容时，返回执行计划并填写修改需求重新生成。

## 4. 复合测试

一个需求可以包含多个渠道。只有描述同一业务目标、共享前置状态和结果判断的操作才放进同一个场景；互不依赖的检查应生成不同场景，避免一次失败阻塞无关测试。

第二层将同一场景拆成一个 flow 内有序的 executor stages。顺序来自该场景的实际依赖，不存在所有测试都必须遵守的固定流水线。例如：

```text
API 准备数据
  -> UI 或 API 执行核心行为
  -> 数据库读取验证
  -> 清理
```

性能基线、端口连通性等若不依赖上面的业务状态，应分别成为独立 flow；只有需求明确说明依赖时才进入同一条链。

每个 stage 只能使用一个 executor，顺序由 `stage.order` 决定。前一个 stage 失败时，后续 stage 不执行并标记为 blocked。
连续的 UI 操作应集中在一个 UI stage 内，避免浏览器会话被拆开。需要“第 4 次操作后马上数据库验证，再继续 UI”的场景，应拆成两个独立场景或等待执行器提供会话级交错协议。

复合测试的每个操作和预期结果仍保留第一层来源 ID，报告按 flow、stage 和 step 展示结果。
